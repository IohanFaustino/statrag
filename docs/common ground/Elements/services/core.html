Per-module deep-dive

config.py — centralized runtime configuration

Defines a single Settings class (Pydantic BaseSettings, line 20) that loads from a .env file at the project root (ROOT / ".env", line 23–27) with extra="ignore" — unknown env vars are silently dropped rather than raising. The singleton settings = Settings() (line 108) is instantiated at import time; every pipeline module imports from this one object so changing a model ID or port requires only a .env edit, no code change.

Alongside Settings, four module-level Path constants are defined (lines 13–17): ROOT, DATA_DIR, RAW_DIR, and BM25_DIR / BM25_PICKLE. These are used by ingestion to locate on-disk artifacts and are exposed at module level (not as settings fields) because they are always derived from the repository root — not configurable.

The parsed_use_v2_modes() method (lines 101–105) handles the comma-separated env-string edge case: USE_V2_MODES can arrive from the environment as a plain string ("*") or as a JSON list; the method normalizes both forms.

qdrant_store.py — Qdrant client and collection bootstrap

Provides three things: a lazily created singleton client, a naming convention function, and two idempotent collection-bootstrap helpers. All three are imported directly by both ingestion and the chat-service retrievers.

Module-level constants (lines 27–30) define the named-vector keys used across the entire system: DENSE_DIM = 3072, TEXT_VECTOR = "text", SPARSE_VECTOR = "bm25", IMAGE_VECTOR = "caption". Any code that reads or writes these vectors imports from here — there is no duplication.

client() (lines 33–40) is decorated with @lru_cache(maxsize=1) — the first call creates a QdrantClient connecting to settings.qdrant_host:settings.qdrant_port with prefer_grpc=False. The qdrant_api_key is passed only when non-empty (or None). All subsequent calls in the same process reuse the same connection.

collection_names(field) (lines 43–48) strips and lower-cases the field slug then returns the tuple ("{field}_textbooks", "{field}_images"). The field comes from the per-book YAML (src/ingestion/books/<slug>.yaml). Passing an empty string raises ValueError (line 47). This function is the single source of truth for the naming convention — callers never construct collection names manually.

ensure_text_collection(name) (lines 51–65) creates the text collection if it does not already exist. It fetches the set of existing collection names (line 53), then calls create_collection with two vector configs: a named dense vector (TEXT_VECTOR, 3072d, cosine distance) and a named sparse vector (SPARSE_VECTOR, BM25, on_disk=False). Existing collections are silently skipped — this makes the function safe to call at the start of every ingest run without extra guards in callers.

ensure_image_collection(name) (lines 68–79) follows the same pattern but creates a dense-only collection using the IMAGE_VECTOR ("caption") key at 3072d cosine. Image collections have no sparse index because captions are short and lexical BM25 adds no value over the dense embedding of caption text.

Auto-create gotcha: collections are created on first ingest, not on application startup. A query against a field that has never been ingested will fail with a Qdrant "collection not found" error. The retrieval service handles this by iterating only over collections that actually exist in Qdrant (via client().get_collections()).

Rationale & invariants

Why core imports nothing in-repo — the Chinese wall

The rule is stated verbatim in src/core/__init__.py (lines 3–7): "core/ depends on NOTHING in the repo (only third-party libs). ingestion/ and services/ may import from src.core. core never imports from ingestion or services."

There are three concrete benefits to enforcing this wall:

  • No import cycles. Ingestion and services can both import core freely. If core imported either of them, a service importing core would create a cycle and Python would raise an ImportError on startup.
  • Single source of truth for infra. All LLM model IDs, ports, collection names, and weights live in one place (Settings). Changing a default requires one .env edit, not a grep across a dozen service files.
  • Testability. Because core has no in-repo dependencies, it can be imported and tested in complete isolation — no mocking of ingestion pipelines or chat service state needed. The one-shot verification script in docs/system/invariants.md imports only src.core.qdrant_store.client and src.core.config.settings.

The Chinese wall also bounds how a future new service can go wrong: a badly behaved src/services/new_service/ can only harm itself — it cannot corrupt the shared Qdrant schema or the singleton Settings object because those live in core and are read-only at runtime.

Relevant invariants from docs/system/invariants.md

The invariant document covers over 37 numbered invariants for the ingestion and chat-service layers. The following are the most directly relevant to the core layer:

  • Invariant 16 — Image collections ({field}_images) MUST exist before any tutor query routes there; ensure_image_collection runs inside _persist_images (auto-creates). Upserts MUST be chunked at ≤ 100 points per batch to avoid Qdrant write timeouts.
  • Invariant 37 — The formula_cache Qdrant collection is auto-created on first write by the formula-recovery stage; lookup gates on score ≥ 0.93. This follows the same ensure_*_collection pattern provided by qdrant_store.py.

Invariants 1–11 govern ingestion payload shape (field presence, synopsis type, token count) and are verified by the one-shot script that directly calls client() from src.core.qdrant_store. Invariant 12 governs the dark-theme CSS token. Invariants 13–36 govern the chat-service pipeline stages. None of these add further constraints on the core module itself beyond the Chinese-wall rule documented in __init__.py.
